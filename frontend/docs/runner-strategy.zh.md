# Runner 与任务

服务器内嵌 runner 组件:任务图模型、调度器以及通往测试环境的 SSH 传输。
原先的 sshcheck 包(SSH 传输)已并入其中。

## 派发

**任务图**由三种触发方式之一创建 —— webhook 推送、手动 yaml 矩阵派发、
手动自定义命令派发。三者共用同一套图模型、调度器和环境执行流程;区别
在于提交与各阶段命令如何确定,以及重复触发时的记录方式。

- **webhook 派发**(自动):向已配置代码仓库的推送(见
  [Webhooks](#/docs/webhooks))会在**被推送的提交**上读取
  `md-builder.yaml`,按标签把条目匹配到已启用的环境,每个条目创建一条
  图。图以(提交, 环境)为键:重复推送同一提交 —— 或在修改环境标签或
  YAML 后通过 `POST /api/jobs` 重新派发 —— 是**重排**既有图,而不是
  替换它。节点按其 node key(阶段类别,或用例的 `regression:<用例名>`)
  匹配,因此重新派发会在仍然存在的节点上按新配置快照开启新一次尝试,
  把早先尝试的历史留在原处,并**退休**(retire)新 YAML 不再定义的
  节点 —— 但从不删除:被移除的用例保留自己的运行、日志和工件,不再被
  调度,也不再参与汇总。不必有人手动触发,同一个版本也会这样被重排:
  推送分支后再为它开 MR,会在同一行提交上把同一张(提交, 环境)图
  派发两次,而第二次派发会把还在跑的东西重新开始(见
  [Webhooks](#/docs/webhooks))。读取 YAML 本身
  是向代码主机索取一个文件的一次请求,完整克隆只作回退,且有超时上限
  —— 所以派发耗时与仓库大小无关,沉默的仓库服务器也无法让它一直挂着
  (见 [Webhooks](#/docs/webhooks))。
- **手动 yaml 派发**(**Run command** 页面的 *Manual test* 标签的
  第一部分 —— 一个 ref 输入框 + 一个按钮 —— 或
  `POST /api/jobs/manual-yaml`):按需执行的 webhook 流程。解析站点配置
  代码仓库的一个 ref(分支 / 标签 / 提交 id,留空 = HEAD),提交行按
  **webhook 同样的去重方式**记录,然后与推送完全一致地派发该提交上的
  yaml 矩阵:图同样以(提交, 环境)为键,重复触发同一 ref 会以最新快照
  重排这些图(采纳 yaml 或环境标签的修改),而不会新增矩阵行。图标记
  `trigger: 2`。
- **手动派发**(**Run command** 页面的 *Manual test* 标签,或
  `POST /api/jobs/manual`,见[仪表板与 API](#/docs/dashboard)):用户
  自定义的测试 —— 不需要 YAML,也不需要推送。仓库默认取站点配置的
  代码仓库(也可以填写其他地址覆盖);可选的分支 / 标签 / 提交会在派发
  前解析为具体提交(留空 = HEAD);构建 / 单元 / 回归命令来自表单:
  留空的阶段直接不进入图(矩阵单元格显示"—"),每个阶段按默认超时
  (1 小时)运行。可以勾选你有权使用的环境的任意子集(默认全选)——
  自己的,管理员则是全部;每个环境创建一条图。与 yaml 流程不同,这里
  不是标签匹配:环境由调用方指定,并且接口会拒绝调用方无权管理的环境
  (`403`)—— 阶段命令会用环境所有者的私钥在那里执行。
  与 webhook 推送不同,每次手动派发都会记录**一条新的
  commit 行**:重跑同一 ref 时,每次尝试都有自己的矩阵行(commit
  message 携带派发时间),同一(repo, sha)的旧行会被标记为
  **superseded**(已过期)—— 仍显示在仪表板上,但置灰。

任务的 `trigger` 列记录图的创建方式 —— `0` = webhook,`1` = 手动
(自定义命令),`2` = 手动 yaml ——
并透出到任务页面和矩阵上(手动创建的图 —— `1` 或 `2` —— 带一个小的
"M" / "manual" 徽标)。

**各入口使用哪些环境。** 环境是全站共享的资源池(见
[测试环境](#/docs/environments)),因此 yaml 流程和 **Run command** 页面
的两个选择框覆盖的范围并不相同:

| 入口 | 环境 |
|---|---|
| webhook 推送、**手动 yaml 派发** | 全站所有**已启用**环境,每个 yaml 条目按 tags 匹配一个 —— 一次运行可能落在别的账号注册的机器上 |
| **Exec / script** 标签(**Run command**) | 你有权使用的环境:自己的,管理员则是全部 —— 命令会用环境的私钥登录 |
| *Manual test* 标签的**手动派发** | 同一集合(选择框,且接口会拒绝别人的 id);环境是显式指定的,不做匹配 |

运行环境列表和 dashboard 矩阵始终展示整个资源池,并标注每个环境的 owner。

一条任务图 = 一个 root 任务加一小组子任务树:

```
root (test <sha> on <environment>)   # 虚拟:代表整条管线
 ├─ clone repositories               # 服务器克隆,经 SSH 上传 tar
 ├─ build                            # 构建命令,在其 workdir 中
 ├─ unit tests                       # 每阶段命令,独立超时
 └─ regression       (虚拟)          # 阶段容器:汇总其用例
     ├─ regression: heat             # 每个选中的预设一个子任务
     └─ regression: poisson
```

- 每个节点都是 `tasks` 表中的一行;`kind` 列区分 root / clone / build /
  unit / regression(容器)/ regression_case(列表是开放的 —— 未来的
  类别,例如性能测试,只需增加一个常量和一个执行器)。
- 存储了两种关系,含义并不相同。`parent_id` 是**树**:节点嵌套在哪里,
  这既是图页面绘制的内容,也是汇总时遍历的结构。`depends_on` 是
  **调度 DAG**:一个 JSON 任务 ID 数组,其中的任务都结束后该节点才
  就绪。容器永远不会成为依赖(它的状态是推导出来的,指向它的边永远
  不会就绪),root 同样不会:`UpsertTaskGraph` 会拒绝这两种情况。实际
  上图里用例依赖 build(条目没有构建阶段时依赖 clone),其余节点依赖
  它前面的那个节点。
- 回归阶段在构图时展开:条目选中的每个预设(`regression.use` 减去
  `disable`;见[测试矩阵](#/docs/test-matrix))都成为名为
  `regression: <预设>` 的**独立真实任务**,嵌在虚拟容器之下,依赖
  build,拥有自己的命令、workdir、超时和工件文件。用例是任务而不是
  父运行结果里的若干行,这正是它们能并行执行、各自保有自己的日志和
  尝试历史、并在重新派发后存活的原因。
- 虚拟节点 —— root 和回归容器 —— 什么都不执行,也不记录任何结果:
  它们的状态、计数、摘要和时间戳永远由子节点**汇总**得出,因此不可能
  与各阶段实际做的事脱节。容器把真实子节点各算一个单位,把虚拟子节点
  按其自身子节点的计数计入,因此回归阶段的数字是用例的,root 的数字是
  整条管线的。
- 每个节点保存其配置的**快照**,因此后续修改 YAML 或手动重新派发都不
  影响已在运行的图。
- 子任务未能通过时 —— 它失败了、超时了,或它自己就被上报为 `skipped`
  —— 所有 (传递地)依赖它的任务被标记为 **skipped**,原因写在摘要里,
  日志中也有一行对应内容(`skipped: upstream task build failed`,或
  `upstream task build timed out`)。依赖必须
  通过,其后的节点才算就绪,因此一个永远不会通过的节点不会留下任何
  可等待的东西:跳过与结果记录在同一个事务中完成,不会留下无法排空的
  队列。`skipped` 与 `passed`、`failed`、`timeout` 属于同一词表中的真实状态,而
  不是显示层的约定:该节点从未执行过,仪表板如实呈现。完全不属于图的
  阶段(手动派发中留空的阶段命令,或后续派发移除的用例)不算"跳过"
  —— 它根本不存在,单元格显示"—"。

## 执行池

- 默认 2 个 worker goroutine 原子地认领就绪的子任务并运行,每 2 秒轮询
  一次。子任务在其全部依赖完成后即为就绪。执行池大小由服务端配置文件的
  `worker.count` 决定(也可用环境变量 `MD_BUILDER_WORKERS`);
  `worker.enabled: false`(或 `MD_BUILDER_DISABLE_WORKER=1`)完全关闭执行池
  (派发仍会记录任务)。
- 服务器崩溃后遗留的 `running` 任务在启动时被重置为 pending 并重新
  执行。

## 每个子任务

- **clone**:*服务器* 克隆被推送提交上的代码仓库(测试输入内置于其中,
  或由代码自行获取),打包为 tarball 并经 SSH 流式传到环境(解压为
  `~/.md-builder/tasks/<sha12>/code`),随后把环境的环境设置脚本(若
  已配置)写入任务目录。远程主机**不需要 git,也不需要任何仓库访问
  权限**。
- **build**:根据配置快照生成的 bash 脚本经 SSH 流式送到环境
  (`bash -s`),在阶段的工作目录中运行构建命令
  (设置了 `build.workdir` 时为源外构建),由远程 `timeout` 命令按配置
  的超时约束(细节见[测试矩阵](#/docs/test-matrix))。构建结果会记录
  为一条 "build" 测试运行,显示在仪表板的构建矩阵上。
- **unit**:同样方式在其工作目录中运行阶段命令。阶段的完整输出流入
  任务日志;阶段可以打印一行 `MD-BUILDER-SUMMARY: <text>` 来自行声明
  一段式结论,否则存储退出码加日志尾部。结果被记为一条测试运行(见
  [仪表板与报告](#/docs/dashboard))。
- **regression: <预设>**:预设的命令在预设的工作目录中、导出 `MD_CASE`
  后运行,用例的工件文件被收集到该用例**自己的**运行上。不会写入任何
  父运行:上面的回归容器是虚拟的,它的 "N/M cases passed; failed: heat"
  摘要就是其下用例节点汇总的结果。
- 被 **skipped** 的阶段完全不会建立 SSH 会话:调度器直接关闭它那条
  pending 尝试并写入原因,得到一句摘要和一行日志 —— 因此被上游失败
  终止的阶段与执行后失败的阶段可以区分开。

每个阶段脚本都经过相同的导言:

```bash
export MD_COMMIT=... MD_ENV_NAME=... MD_ENV_TAGS=...
export MD_TASK_DIR=~/.md-builder/tasks/<sha12> MD_CODE_DIR=$MD_TASK_DIR/code
export MD_CASE=...                    # 仅回归用例子任务
export <条目 env 映射>
ENV_SCRIPT="$MD_TASK_DIR/md-builder-env-<hash>.sh"
if [ -f "$ENV_SCRIPT" ]; then . "$ENV_SCRIPT"
else echo "warning: env script $ENV_SCRIPT not found; continuing without it" >&2; fi
cd "$MD_CODE_DIR/<workdir>"           # 空 workdir 即代码目录
<受 timeout 约束的阶段命令>
```

环境脚本最后被 source,因此它可以覆盖已导出的变量(见
[测试环境](#/docs/environments))。每个阶段都是独立的 SSH 会话,这也
是导言对每个阶段重复执行的原因。

## 日志

每个子任务的输出增量存入 `task_logs` 表,且**以(任务, 尝试, 序号)为
键**:每块一行,至少每 2 秒或每 32 KiB 一块。以尝试为键正是把重试的输出
与上一次隔开的东西 —— 跟随当前尝试与回看早先某次尝试,只是同一条查询
换一个 `attempt`。前端轮询 `GET /api/tasks/{id}/log?after=<seq>` 获取
新块,因此运行中的任务可以实时跟随;`GET /api/tasks/{id}/log/download`
把整次尝试作为单个文本文件流出,按批次从存储的块拼出。一次读取返回一页
(1000 块),只要返回的页是满的,查看器就继续索取下一页,因此长日志会被
读到末尾,而不是停在第一页结束的地方;阶段结束时,查看器在定时器停下
之前还会再读一次,最后几行和阶段收尾时写下的摘要因此都在。日志按每次
尝试封顶 8 MiB;完整日志保存在服务器端,界面显示尾部。

## 任务 API

- `GET /api/tasks/{id}` —— 单个任务;root 附带其节点列表(当前图,加上
  后续派发丢弃的已退休节点)以及提交/环境上下文。
- `GET /api/tasks/{id}/runs` —— 该任务的各次尝试,最新在前;日志查看器
  的尝试切换器读的就是它。虚拟任务返回空列表。
- `GET /api/tasks/{id}/log?after=<seq>&attempt=<n>` —— 给定序号之后的
  日志块(增量式,用于实时跟随)。不传 `attempt` 时读取当前那次尝试。
- `GET /api/tasks/{id}/log/download?attempt=<n>` —— 该次尝试的完整日志,
  以 `text/plain` 附件返回。
- `GET /api/tasks/{id}/artifacts/zip` —— 子树最新尝试的工件:被指定任务
  的文件在归档根目录,每个后代的文件放在以它命名的目录下;一个回归阶段
  因此会作为一个包含其全部用例的包下载(见
  [仪表板与报告](#/docs/dashboard))。

读取以上任何一项都对所有已登录用户开放:矩阵本身是全站级的,它的下钻
页面同样如此。矩阵中虚拟节点的单元格携带 `runId` 0(它没有运行),因此
指向任务页;而每个真实节点从被派发的那一刻起就有一条运行,见下。

## 结果处理

阶段的结局只在一个地方写入:`store.FinishAttempt`。它记录该次尝试的运行
(状态、摘要、错误、计数、工件、时间),用同一批数字刷新节点的缓存值,
再把虚拟容器自底向上重新汇总。阶段结束时 runner 在进程内调用它;经
HTTP 到达的报告则由 `POST /api/test-runs` 调用它。只有这一条写入路径,
意味着节点、它的运行以及它上面的容器不可能彼此不一致。

- SSH 连接失败、构建失败或阶段命令以非零退出时,子任务进入
  **failed**(错误记录在任务及其详情页上)—— *测试本身* 的通过/失败
  体现在仪表板上,而不是任务状态里。
- 阶段命令超出其超时则进入 **timeout**:同样的阻断效果,但是独立的
  状态 —— 错误列里写着超时与命令,日志中有一行 `task timed out: …`,
  摘要尾部是日志的最后几行。如果某个容器下的失败全部是超时,它自己也
  取 `timeout`,因此被时钟叫停的管线读起来就是超时。
- **单元测试运行**在命令非零退出 **或** 工件文件解析出失败用例时为
  failed(ctest 一类的包装可能吞掉测试程序的退出码)。它们只带聚合
  计数(总数 / 通过 / 失败 / 跳过,`total` 把每个用例都算一次,包含
  skipped),跨所有配置的工件文件求和;逐测试明细由浏览器从存储的工件
  文件解析。
- **回归用例**仅凭其命令的退出状态判定(退出码 0 → 通过;其他任何
  情况 —— SSH 失败、非零退出 —— → 失败,超时则为 `timeout`);其
  `artifacts` 文件挂在该用例自己的运行上、只作展示存储,不会翻转判定。
  其上的容器负责汇总:任一用例失败则该阶段失败,摘要读作
  "3/4 cases passed; failed: heat";若它下面的失败全是超时,则读作
  "1/4 cases passed; timed out: poisson"。
- 容器的摘要描述的始终是自己的汇总,而不是某次上报:
  "3/4 cases passed; 1 in progress"、"2/4 cases passed; 2 queued"、
  "4/4 cases skipped (upstream failure)"、"4/4 cases passed"。
- 没有自动重试:重新推送提交或重新执行派发会为每个节点开启新一次尝试。

### Artifact 与回归扩展

工件文件统一存在 `test_artifacts` 表中,按运行关联 —— 一次运行可以有多
条。工件归属产出它的运行:单元测试阶段的结果文件挂在单元测试运行上;
回归用例的文件挂在该用例自己的运行上。由于用例本身就是带运行的任务,
回归的扩展无需引入新概念:逐用例日志和系列(画图)数据将作为
`log` / `series` artifact 存在同一张表里、挂在用例的运行上,由浏览器的
"分析"视图取回展示。

## 尝试生命周期

运行在阶段执行**之前**就存在,因为承载它的节点与它同时创建。派发时每个
真实节点开启一次尝试(`BeginAttempt`):节点回到 `pending`、计数清空,
并为它创建一条状态为 `pending` 的第 N 次尝试运行:

```
派发              认领                     结果
pending(运行)  →  running            →     passed/failed/timeout/skipped
                  (ClaimReadyTask)          (FinishAttempt)
                                            cancelled (CancelGraph)
```

- 调度器原子地认领就绪节点(`ClaimReadyTask`),在一个事务里把节点与其
  进行中的运行一起翻转为 `running`,并在同一个事务中把容器重新汇总
  —— 阶段在跑的图读作 `running`,而不是排队中。矩阵单元格显示转圈
  图标,运行页实时跟随(运行 3 秒轮询、日志 2 秒轮询)。调度器看的是
  整个队列而不是其中固定的一段窗口,因此无论前面堵着多少无法认领的
  节点,就绪节点都会被派发出去。
- 阶段结束时,`FinishAttempt` 用结果关闭这条运行:状态变为终态,日志
  停止增长,runner 取回的工件挂到这条运行上 —— 即产出它们的那次尝试,
  而不是整个任务。
- 上游阶段失败、超时或被上报为 `skipped` 时,下游仍在 pending 的尝试
  以 **skipped** 关闭并写入原因(一句摘要、一行日志),容器随之汇总为
  `skipped`、`failed` 或 `timeout`。
- 对已经结束的尝试再次报告**不会**覆盖它:存储层会开启**下一次尝试**
  —— 一条新运行,任务计数器递增 —— 两条记录都保持可读。这就是重试
  路径,也是为什么运行的 `attempt` 序号属于它的身份:`(任务, 尝试)`
  唯一,日志以此为键,运行页因此能够提供早先几次尝试。
- 阶段在飞行中时发生**重新派发**:节点以新的尝试重新武装,被顶替的
  那次尝试的运行被关闭(状态 `skipped`,摘要为 "superseded by a new
  dispatch of this task")—— 否则再没有任何东西会关闭它。runner 报告
  的是它实际执行的那次尝试(报告里带着尝试序号),因此旧尝试保留真实
  结果,新尝试留给调度器真正执行。
- `pending`/`running` 是仅有的两个非终态;其他任何状态都是最终状态。
  重新执行派发会开启新的尝试;没有任何内容被原地改写。
- 节点也可能以 **cancelled** 收尾 —— 这是对*运行*的决定,不是对代码的
  判定:站点的重复 commit 策略把它丢掉了(`fork_cancel`,见
  [站点配置](#/docs/site-configuration)),或者是 runner 中止了它正在执行
  的阶段。状态与摘要同时写在该节点与那次尝试的运行上,并且只有未完成的
  工作会被取消:已经通过的节点保留它的状态、结果与日志(见
  [测试矩阵](#/docs/test-matrix))。
- **取消**在同一个事务里把进行中尝试的运行以 `cancelled` 关闭并取消该
  节点,因此读者不会看到"已取消却仍有一条实时运行"的节点。runner 正在
  执行的阶段同时被中止(其下的 SSH 会话被关闭);它随后送来的结果会被
  `FinishAttempt` 拒绝(记为"the task was cancelled"),而不会覆盖这次
  取消。取消对*报告*是吸收态 —— 晚到的结果既不复活该节点,也不在其后
  开启新尝试 —— 但对*派发*不是:触发取消的策略仍在生效期间,这一行不会
  再被派发("再跑一次这个版本"在新策略下意味着新的一行),可一旦某一行
  真的被再次派发(站点改回 `requeue`,同一版本的推送于是重新落到该行),
  整张图都会以新的尝试重新跑一遍,被取消的那次尝试作为历史保留。

## Demo 种子与冻结的实时图

`seed` 子命令为演示数据库填充两类图,它们也恰好是两种调度模式行为的
参照。它用生产环境的构图器建图,并通过 runner 使用的同一批存储调用收尾
(`FinishAttempt`,以及上游失败时停止阶段的跳过路径),因此种子矩阵与真实
派发出来的矩阵无法区分 —— 包括各次尝试、按尝试存储的日志和工件。

- **已完成的图**(较旧的提交):每个真实节点都处于终态尝试,带日志块,
  以及(单元与构建阶段的)runner 本会取回的工件文件。这里没有任何可被
  认领的任务。
- **实时图**(最新的提交):一张执行中的快照 —— 一张图处于构建中
  (clone 已完成、build 为 `running` 且有部分输出、各测试阶段仍排队中),
  一张完全未被认领。它们的尝试是真实的 `pending`/`running` 运行,因此
  矩阵单元格、运行页和日志轮询的表现与真实派发完全一致。

调度器对实时图一视同仁;区别完全取决于演示的启动方式:

- 设置 `worker.enabled: false`(或 `MD_BUILDER_DISABLE_WORKER=1`)时执行池
  关闭:快照永久冻结 —— 没有任何节点被认领,pending/running 的尝试停在
  原处,日志不再增长。适合稳定的演示。
- 开启 worker 时,实时图的 pending 阶段**会被认领并真实执行**
  (并在不可达的演示 SSH 主机上失败):各次尝试经由 running 变为
  failed,下游阶段被跳过并上报,root 变为 failed。注意服务器重启还会
  把 `running` 任务重置为 pending(崩溃恢复),所以只要执行池开启,
  冻结的"运行中"演示就会重新变得可被调度。
- 重复播种是幂等的:提交按(repo, sha)去重,已经完成的单元格保持不动
  (`-force` 会先删除演示环境的任务及其运行、日志和工件,把所有图重建
  一遍)。

## 前置条件

- **服务器** 需要对代码仓库有读权限(读 YAML 和克隆)—— 公开仓库开箱
  即用,私有仓库使用站点设置中配置的 Project Access Token(项目访问
  令牌,见[站点配置](#/docs/site-configuration))。克隆通过 go-git 在
  进程内完成:服务器**不需要**安装 `git`。
- 每个**远程环境**需要 `bash`、`tar`、`gzip` 和 `timeout`,以及构建与
  测试命令所需的工具链。它不需要 git,也不需要仓库访问权限。
